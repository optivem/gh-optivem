# 2026-08-10 10:14:12 UTC — Close the two no-retry gaps in `deploy-docker-compose` that fail the acceptance stage on transient registry errors

## TL;DR

**Why:** gh-optivem run [31365614953](https://github.com/optivem/gh-optivem/actions/runs/31365614953) failed two matrix legs (`multitier/multirepo/typescript/dotnet` job `93391979695`, `multitier/monorepo/typescript/dotnet` job `93391979701`). Both surfaced identically — `TestValidMultitierConfigurations` failing at `internal/config/config_system_test.go:292` with "expected exit code 0, got 1" — but the real cause is two *independent* holes in `optivem/actions/deploy-docker-compose@v1`, where a transient Docker registry error is not retried: (A) `docker compose up -d` is not wrapped in `retry_run` at all, so a Docker Hub `502 Bad Gateway` while resolving a `# syntax=docker/dockerfile:1.4` directive killed the run outright; (B) GHCR's secondary-rate-limit `403` is worded like an auth denial (`denied: permission_denied` / `Forbidden`), so `_RETRY_HARD_FAIL` classifies it as a hard failure and `retry_run docker compose pull` passed it through with zero attempts (step duration `1799ms` — no backoff). Neither is a product bug: the scaffolded apps, the shop templates, and the Go system test are all innocent.

**End result:** Every Docker registry call in `deploy-docker-compose` retries on transient failure. `docker compose up -d` is wrapped in `retry_run`, GHCR secondary-rate-limit `403`s are reclaimed as transient by `_RETRY_FORCE_RETRY` (while genuine auth `403`s still fail fast), and the docker deploy path backs off long enough (~5.5 min) to outlast a GHCR rate-limit window. Regression tests pin both behaviours, and gh-optivem's vendored `retry.sh` is re-synced — clearing pre-existing drift as a side effect.

## Outcomes

What we get out of this — the goals and deliverables:

- A Docker Hub or GHCR blip during `docker compose up -d` no longer fails the acceptance/QA/prod stage — the command retries like `docker compose pull` already does.
- A GHCR secondary-rate-limit `403` is treated as transient and retried, instead of being misread as an auth denial and failing instantly with zero attempts.
- A *genuine* GHCR auth denial (no rate-limit wording) still fails fast — the fix is deliberately narrow and does not blunt the hard-fail list.
- The docker deploy path waits long enough to outlast a GHCR rate-limit window (~5.5 min across 5 attempts), without slowing down the `gh` / `sonar` / `git` retry paths that share the same engine.
- Two regression tests in `_test-retry.sh` lock in both the reclaim and its narrowness, so a future edit to the regexes can't silently reintroduce either gap.
- `gh-optivem/.github/scripts/retry.sh` is regenerated from canonical and back in sync — its banner SHA currently pins `40dd2a5` while canonical is `47823a6`, so it is also missing the `scanner.sonarcloud.io/jres` and `binaries.sonarsource.com` force-retry clauses.
- All 12 shop stage workflows (monolith/multitier × dotnet/java/typescript × acceptance/qa/prod) inherit the fix from the single shared composite — no per-language fan-out needed.
