# 2026-11-09 12:02 UTC — Refactor & Review: UX/UI review

## TL;DR

**Why:** Acceptance tests don't check UI consistency or naming. In Green the agent can make a yes/no field a checkbox on one page and a dropdown on another, or say "order" on one screen and "purchase" on the next. The executor/reviewer/approver article and the Circle session describe a UX/UI review:
1. Start the app.
2. A reviewer agent checks UI and naming consistency. It reports findings and makes no changes.
3. The human reviews too, and the two reviews become one plan.
4. The agent executes the plan.
5. Restart the app and do a visual check.
6. Issues feed the guidelines.

**End result:** The `refactor` menu offers "UX / UI Review", running that loop.

## Decisions (proposed 2026-11-09, pending user OK — override any line)

- **The reviewer sees the UI two ways: screenshots plus the UI source.** A deterministic service task (`capture-ui-screens`, no agent) starts nothing new: it reuses the app the cycle already started and the UI channel's base URL, drives headless Playwright (already a dependency of every scaffolded system test: Java via `build.gradle`, TS via `@playwright/test`) over the pages the UI driver adapter visits, and saves one screenshot plus the page text per page to a temp folder. The agent reads those images and the frontend source. Reading templates only would miss rendered inconsistencies; letting the agent drive a browser itself would be non-deterministic and expensive.
- **CI is out of scope.** The review is an interactive `refactor` menu option, like the Code & Architecture Review: it needs a human, so it never runs headless in a pipeline. Capture failures (app not up, page error) fail loudly.
- **The "visual check" is a human-tier approve gate inside the CLI** (`APPROVE_VISUAL_CHECK`, category `human`) after the restart: "Does the UI look right?" A "no" asks for issues one per line and feeds the same guidelines loop as the code review (`guidelines-updater`, `${guidelines-path}`, UI rules in `ui.md`), capped at 3 rounds.
- **Reuse, don't copy:** the process mirrors `review-code-and-architecture` (reviewer → human merges findings into one plan → refactorers execute → restart → visual check → guidelines). If the shared part is large, extract it into one sub-process both reviews call.
