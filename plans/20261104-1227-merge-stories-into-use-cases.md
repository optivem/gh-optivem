# 2026-11-04 12:27 — Merge each user story into the use cases before ATDD builds it

## TL;DR

**Why:** Use cases are the heart of the spec: a use case narrative is what the system does, and its `UC-NNN.M` acceptance criteria are just the narrative's paths flattened (main scenario + each extension). User stories are the increments: each one adds or modifies criteria, which logically means a change to the narrative. Today an ATDD story ticket carries its own acceptance criteria and never touches `docs/use-cases/`, so the use cases go stale and requirements live in two places.
**End result:** Teams keep writing user stories as they do today (GitHub or Jira). At the start of ATDD, an agent merges the story into the use cases (narrative + criteria), the user approves that change, and the acceptance tests then trace to the updated `UC-NNN.M` criteria. The merge is one-way and one-time: the story is closed after it is built and never re-edited, so the use cases are the single current spec and the stories are history.
**What the user sees:** after a story is picked up, the agent shows a proposed use case diff (narrative step/extension + `UC-NNN.M` lines, or a brand-new `UC-NNN` file in a repo that has none yet) and waits for approval; a no-op merge passes silently. `gh optivem spec status` shows the story's new criteria as unverified, a criterion whose text changed since its test was written as changed/unverified, and both as verified once ATDD goes green.
**Unchanged:** the story ticket format (Description + Gherkin Acceptance Criteria), bug and task tickets, the rest of the ATDD flow, and test tags (`@Tag("UC-001.4")`).

## Outcomes

- **Stories stay the planning and tracking unit** (sprint, estimate, priority, status), unchanged for GitHub and Jira teams. No team has to edit markdown use cases by hand.
- **One-way, one-time merge at intake:** a new first step in the ATDD story flow proposes the use case change for the story's criteria:
  - which use case(s) it changes, or a new use case
  - the narrative edit (new or changed step / extension)
  - the added or modified `UC-NNN.M` criteria
  The user approves the change before any test is written. **When the merge changes nothing** (the story's criteria already match the use cases, e.g. stories generated by `gh optivem kickoff`), it passes without a human approval, so unattended runs don't stall. No two-way sync: once merged, the story is not re-edited (a later change is a new story).
- **Contradictions are flagged, not overwritten:** when the story conflicts with what a use case already says, the merge stops and asks, instead of silently replacing behaviour.
- **Modified criteria show as unverified:** `gh optivem spec` notices when a criterion's text changed since its test was written (a **criterion fingerprint** stored in the spec state file that grows out of today's `.spec-baseline.json`; distinct from the kickoff plan's approval fingerprint, though they may share hashing code) and marks it unverified, so a passing old test cannot hide a changed requirement.
- **Consistency check:** every criterion on the story maps to a criterion in the updated use case, and the acceptance tests reference those `UC-NNN.M` ids.
- **Bugs and tasks are unchanged:** a bug means the system does not match the spec (no spec change); tasks are refactors/infra.
- **Tracker-neutral design:** nothing assumes GitHub-only, so a later Jira tracker backend fits without redesign (today only `github` and `markdown` backends exist under `internal/atdd/runtime/tracker/`).

## Resolved decisions

- **Who writes the narrative change** (2026-11-04): the merge agent proposes the narrative + `UC-NNN.M` diff from the story; the user approves. Keeps story-writing as light as today and works for Jira product owners who never touch markdown.
- **Story criteria format** (2026-11-04): Gherkin stays on the ticket, so today's ATDD intake contract is unchanged; the merge derives the prose `UC-NNN.M` lines and the narrative edit from the Gherkin.
- **Criterion fingerprint storage** (2026-11-04): extend the machine-managed file `gh optivem spec adopt` already writes (`<specDir>/.spec-baseline.json`, `internal/spec/config.go`) into a general spec state file holding both `baseline` and `fingerprints` (`{"UC-001.4": "7f3a", ...}`). The hash of a criterion's text is recorded when it first becomes verified; a mismatch later shows it as changed/unverified. No new sidecar file, and test tags stay plain (`@Tag("UC-001.4")`). Rename the file if a more general name fits (e.g. `.spec-state.json`), with no legacy-alias handling.
- **Repos with no use cases yet** (2026-11-04): the first merge creates a new `UC-NNN` file from the story (user approves), so use cases grow story by story; no upfront documentation is required, and existing apps can adopt the flow at any time.
- **How the merge step is built** (2026-11-04, implemented):
  - Node `MERGE_STORY_INTO_USE_CASES` (process `merge-story-into-use-cases`) sits on the story edge of `GATE_TICKET_KIND` in `implement-ticket`, before `CHANGE_SYSTEM_BEHAVIOR`; bugs and tasks skip it.
  - **No-op rule:** the merge is skipped (no agent, no approval) when the story has at least one scenario and every scenario names an existing `UC-NNN.M` id (in a `@UC-001.4` tag, a comment line above the scenario, its title or steps). Kickoff-generated stories must carry the id this way. Anything else goes to the `use-case-merger` agent (human tier, so its PRE and POST approvals are the user's approval of the diff, also under `--auto`).
  - **Consistency check** (`verify-story-merge`): the agent emits `scenario-map` (`<scenario title> => UC-NNN.M`) and optional `contradictions`; the run fails loudly on a contradiction, a validation error in the merged use cases, an unmapped scenario, or a mapped id that does not exist.
  - **Traceability:** the merged ids reach the acceptance-test writer as `${use-case-traceability}` (tag each top-layer test with its criterion ids).
  - The agent runs with `scope: none` because no code-layer scope key covers the use case directory; the POST approval reviews the edit. A dedicated scope key is a possible follow-up.
  - **Fingerprints:** kept in the existing `.spec-baseline.json` (additive `fingerprints` map, schema version unchanged, no rename, so existing `spec.yaml` files keep working). New state `Changed` (tests pass, text edited): strict blocks it, lenient does not.
