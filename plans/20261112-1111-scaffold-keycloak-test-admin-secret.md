# 2026-11-12 11:11 UTC — Scaffold the `KEYCLOAK_TEST_ADMIN_CLIENT_SECRET` repo secret

## TL;DR

**Why:** Shop's cloud acceptance stage now creates a fresh Keycloak customer per test through the `shop-system-test-admin` service account in realm `shop` (shop `30df8177`). Its password comes from a new repo secret, `KEYCLOAK_TEST_ADMIN_CLIENT_SECRET`. Repos scaffolded by `gh optivem init` don't get that secret, so their first cloud acceptance run fails at the `deploy-keycloak` job.
**End result:** `gh optivem init` (and its re-run) makes sure the secret exists on the repo that runs the acceptance stage. It sets a random value only when the secret is missing, and the read-only remote probes report it like the other secrets. No new user input or config field is needed.

## ▶ Next executable step (resume here)

Step 1. Extend `variableSecretPlan` in `internal/scaffolding/steps/github_setup.go`.

## Resolved decisions

- **Value:** generated by gh-optivem (32 random bytes, base64), never asked from the user and never printed. **Why:** nobody needs to know it. Shop's `deploy-keycloak` reconcile step copies the GitHub secret into the Keycloak client on every acceptance run, so any value works and rotating it is safe.
- **Set only when missing** (check via `gh secret list`), instead of overwriting on every re-run like the token secrets. **Why:** a generated value can't be re-derived. Overwriting is harmless, because the next acceptance run re-syncs Keycloak, but it adds needless churn.
- **Which repo:** the repo that runs the acceptance stage (`cfg.FullRepo`; in multirepo, the repo holding `_acceptance-stage.yml`), not the component repos.
